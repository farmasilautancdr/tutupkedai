- **Root-cause fix — payment-zone detection gated on one specific hard-to-OCR line (v2.10→v2.11):** user sent the FULL raw debug text (both passes) for a scan where MASTER showed 0 in the review popup despite being clearly legible in the debug box. Diagnosis: `parseReceiptText`'s `inPaymentZone` only turned on when the exact words "BANK TRANSFER" were found - and in this scan's pass 1, that line didn't OCR at all (not even garbled, just absent), so the ENTIRE otherwise-clean category block (MASTER 199.10, QR PAY 169.00, VISA 572.60, total 2,146.40, all present with correct decimals) got discarded, forcing the noisier auto-enhance pass 2 to run, which is where MASTER's decimal actually got dropped (`MASTER 199 16910`) and the total got digit-corrupted (`2,146.10` instead of `2,146.40`) - landing on the exact wrong final values reported. This is the same "BANK TRANSFER" line that was garbled (as "BATIK THANSFER") in the very first scan reported this session too - two real scans in a row where this specific line was the hardest to OCR, pointing at a structural weakness, not a one-off. **Fix:** zone now opens on ANY known category label (whichever reads cleanly first), not just BANK TRANSFER specifically (`index.html`, `parseReceiptText`). **Found and fixed a second-order regression before shipping**: since pass 1 now succeeds far more often, `mergeOcrResults` was still using a naive "prefer base pass's non-zero value" per field - on a genuinely hard photo, pass 1 could now contribute a wrong-but-nonzero value (from partial, poor-quality zone-opening) that would block a better pass-2 reading it previously never got the chance to override. Changed the merge to prefer whichever pass matched MORE categories overall (a fuller read is more likely accurate line-by-line too), base as tiebreaker. **Verified with the real raw text from both of today's scans plus a synthetic hard-photo case proving the merge fix specifically** (before/after Node unit tests, pure functions, no DOM) - confirmed pass 1 alone now correctly recovers total=2146.40 and MASTER=199.10 for the reported scan (previously landed on total=2146.10, MASTER=0), and confirmed the merge fix prevents a wrong pass-1 value from shadowing a correct pass-2 one in the synthetic case. Bumped `CACHE_NAME`/version to v2.11. **Lesson: when the SAME specific receipt line fails OCR across multiple independent real scans, treat it as a structural gate weakness, not bad luck - don't just patch around individual symptoms (dropped decimals, digit lookalikes) without checking whether an upstream gate is silently discarding otherwise-good reads.**
- **Total-line OCR fix — session total reads 0 even though every category amount is correct (v2.9→v2.10):** new report, same day: debug text showed all 6 legible payment categories correctly matched (MASTER 199.10, QR PAY 169.00, VISA 572.60, etc.) but the total line itself OCR'd as `LG 219640` — the decimal point was dropped entirely (no `.`/`,` survived at all), so `extractAmountOnly`'s strict punctuated-decimal regex matched nothing on that line and the total silently stayed 0. - **Data-loss bug fixed — saved receipt shows 0.00 in the log right after saving (v2.8→v2.9):** user reported the newest saved entry sometimes shows as all-zero in the history log immediately after tapping "Save entry" — happened intermittently, worse on unclear receipts, only ever the newest entry (older entries stayed correct). Initially misread as a leftover OCR issue; ruled that out by comparing the debug OCR text against a real receipt photo — the review-modal numbers were already correct before saving (session total and at least one category matched the physical receipt exactly). Root cause was actually in Drive sync: `loadOutletData()` (`index.html`) fires a background `fetchOutletFromDrive` GET when the outlet screen opens, and its `.then()` unconditionally did `scanHistory = remote.scanHistory || []` with no check for local changes since the fetch was issued. If that GET was still in flight when the user saved (weak signal + a harder receipt needing the auto-enhance OCR retry pass both make this more likely), it would resolve moments later with the pre-save Drive data and silently overwrite/erase the just-saved entry from both `localStorage` and the UI — exactly matching "only the newest entry, intermittent, worse when the receipt's unclear." **Proved this before touching code**: reproduced live in a browser (Playwright) by controlling `fetchOutletFromDrive`'s resolution timing directly — confirmed the entry vanished on the stale resolve pre-fix, and survived post-fix, plus confirmed the legitimate case (another terminal's genuinely newer Drive data, more entries than local) still pulls in correctly. Fix: that callback now refuses to replace local `scanHistory` with a remote version that has *fewer* entries than what's already in memory (signature of a local save the stale fetch doesn't know about) — one guard clause, no other logic changed. Bumped `CACHE_NAME`/version to v2.9. **Lesson: when a user reports "wrong numbers after I did X," don't assume the most recently-fixed subsystem (OCR) is the cause again — verify what's actually on screen at each step first; this turned out to be a sync race, nothing to do with OCR at all.**
- **OCR fix — receipts not catching amount / catching wrong amount on unclear photos (v2.7→v2.8):** two root causes found by reading `parseReceiptText`/`extractAmountOnly` (`index.html`, no build): (1) `extractAmountOnly`'s regex required a strict `\d[\d,.]*[.,]\d{2}` — a single OCR digit-misread-as-letter (O→0, S→5, B→8, I/L→1, G→6, Z→2, common on blurry thermal print) made the whole amount unmatchable, silently returning 0. Fixed by widening the match to tolerate those lookalikes then normalizing the matched token back to digits (`DIGIT_LOOKALIKES` map) — still requires the punctuation+2-digit decimal shape, so it doesn't start matching stray label text. (2) Total-line detection was gated on `matchedCategories >= 5` of the 8 known payment categories (`val_TRANSFER/GRAB/IPAY/MASTER/MISI/QRPAY/VISA/VOUCHER`) — on a blurry receipt where only 2-4 category labels read cleanly, the total was never extracted even when the total line itself was perfectly legible. Lowered the floor to `>= 2` and added a plausibility check (candidate total must be `>= sum of already-matched category amounts`) so a stray smaller number can't be mistaken for the total when the bar is lower. Deliberately did **not** reintroduce matching the "Total Count" label text itself — an existing code comment documents that was already tried and abandoned as unreliable (mangled differently almost every scan). Verified with synthetic garbled-OCR-text unit calls to `parseReceiptText` in Node (pure function, no DOM) comparing old (`git show HEAD:index.html`) vs new behavior — old code returned `total:0` and every category `0` on both a "3-of-8 categories legible" case and a "digit lookalikes" case; new code correctly recovered both.
